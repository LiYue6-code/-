在组长搭好的骨架上，把学生端三个功能从「能点通」补到「符合需求说明书 + 可验收」。

| 需求条目（需求说明书 2.3） | 交付前 | 交付后 |
|---|---|---|
| ③ 学生查询并申请岗位 | 只有关键字模糊搜索，一屏拉完所有岗位；重复申请只能靠后端报错；已下架的岗位详情页照样能点「申请」 | 关键字（岗位/单位）+ 招聘单位双条件筛选、每页 10 条分页；列表和详情页都能看出「已申请」；岗位已截止时按钮自动换成提示；申请前的合法性由 Service 统一校验 |
| ⑤ 就业信息上报（学生侧） | 上报字段没有长度校验，超长直接抛 SQL 异常；被退回时「新建上报」和「补正重报」两张表单同时出现 | 表单校验与表结构长度对齐（单位 100 / 岗位 100 / 薪资 50），保存前统一去空格、空串转 NULL；列表补充重报次数；退回时只保留补正表单 |
| ⑥ 处理进度查询（学生侧） | 只能从「我的申请」「就业上报」列表点进单条记录看时间线，没有汇总入口 | 新增 `/my/progress` 汇总页：申请/上报两类事项一屏查看，带 4 个统计卡与「待补正」提醒；单条时间线补充「状态：A → B」与节点数 |

## 3. 关键设计

### 3.1 岗位检索（`JobQuery` + `JobMapper.xml`）

- 查询条件封装为 `query/JobQuery`，遵循「查询条件用 `query/` 下的对象」的约定。
- 两个条件（关键字、单位）比一行注解 SQL 复杂，按约定写进 `resources/mapper/JobMapper.xml`，接口里只留方法声明，**没有重复定义同一个方法**。
- 学生在读的岗位状态固定过滤为「招聘中」，翻页沿用 `PageResult`，与负责人端列表风格一致。

### 3.2 申请合法性（`ApplicationService.apply`）

一次申请要过四道校验，任一不通过直接返回中文提示、不写库：

1. 已登录（`studentId` 非空）；
2. 岗位存在（`jobMapper.findById`）；
3. 岗位仍在招聘（`Job#isOpen`，即 `status == 招聘中`）；
4. 本人未申请过同一岗位（`job_application` 上有 `uk_job_student` 唯一键兜底）。

通过后写入申请并往 `audit_log` 记一条 `SUBMIT`，学生端时间线因此从「提交申请」开始就是完整的。

### 3.3 「已申请」标记

`ApplicationService.myAppliedJobIds(studentId)` 取当前学生的申请记录并抽出 `jobId` 集合，列表页据此显示徽章、详情页据此隐藏申请按钮。走的是既有的 `findByStudent`，没有新增 SQL。

### 3.4 就业上报的表单校验

`EmploymentService.validateForm` 按表结构长度校验，避免超长数据在 SQL 层报 500：

| 字段 | 约束 |
|---|---|
| `company_name` | 必填，≤ 100 字 |
| `position` | ≤ 100 字 |
| `salary` | ≤ 50 字 |

`normalize` 统一 `trim()` 并把空串转 `NULL`，防止库里出现 `'  '` 这种脏数据。

### 3.5 补正闭环的界面修正

原逻辑用「是否存在待审核/已确认记录」决定是否显示上报表单，一旦记录被退回，上报表单和补正表单会同时出现，学生容易直接新建一条重复上报。现在改为：

```
canReport = 没有在途记录（待审核/已确认） && 没有待补正记录（已退回）
```

## 6. 已知限制 / 后续可做

- 学生暂不能主动撤回申请（需求说明书未要求），如需要可在 `ApplicationFlow` 增加 `WITHDRAW` 动作。
- 岗位检索暂不支持按薪资区间、发布时间排序，条件多了建议在 `JobQuery` 里继续扩展到 XML 的 `<if>` 中。
- 「已申请」标记走的是 `findByStudent` 全量查询，学生申请记录较多时可换成一个只查 `job_id` 的轻量 SQL。
- 进度汇总页只做展示，没有分页；单页超过 50 条时建议换成 `PageResult`。
